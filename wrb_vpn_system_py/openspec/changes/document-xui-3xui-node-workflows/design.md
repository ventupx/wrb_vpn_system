## Context

当前仓库中与 x-ui/3x-ui 节点相关的逻辑高度集中在 `users/views.py`，但同一业务能力以多种触发路径重复出现，包括支付成功后的节点创建、异步重建、续费更新、单节点迁移和整单迁移。`panels/views.py` 与 `panels/models.py` 提供了面板连接参数、登录 cookie、节点列表同步和系统状态查询等基础能力。由于 x-ui 与 3x-ui 的接口路径、请求头、返回节点 ID 的方式以及 x-ui vless 的版本判断规则都不同，维护者目前需要跨多个代码块拼接上下文，风险较高。

这次变更不修改业务行为，而是产出一份根目录 Markdown 文档，并配套 OpenSpec 变更工件，把现有实现中的关键规则以结构化方式固定下来。

## Goals / Non-Goals

**Goals:**
- 明确新建节点时依赖的面板参数、节点参数和协议差异参数。
- 明确 x-ui 与 3x-ui 在创建、更新、迁移节点时的接口路径、提交方式和返回值处理差异。
- 明确 `get_login_cookie` / `make_request_with_cookie` 所要求的面板连接参数和 cookie 刷新逻辑。
- 明确 x-ui 面板在 `vless` 场景下的 `/server/status` 版本判断和 `flow` 字段分支。
- 生成一份根目录 Markdown 文档，供开发、排障和后续改造直接引用。

**Non-Goals:**
- 不重构 `users/views.py` 中的重复创建/迁移逻辑。
- 不修改现有 x-ui/3x-ui 调用接口、字段名或面板交互行为。
- 不为现有流程补充自动化测试或运行时校验。
- 不整理中转站接口，本次仅关注 x-ui/3x-ui 面板和节点相关逻辑。

## Decisions

### 决策 1：以现有代码为唯一事实来源

直接从 `users/views.py`、`panels/views.py`、`panels/models.py` 提炼内容，不依赖外部 x-ui/3x-ui 文档。

原因：
- 项目中已经存在大量定制分支，外部官方文档未必能反映当前实现。
- 用户明确要求提取“项目中”的实际逻辑，而不是通用说明。

备选方案：
- 参考第三方面板文档补全字段解释。
- 放弃原因：会引入与项目实现不一致的内容，增加误导风险。

### 决策 2：文档按“基础参数、创建、修改/迁移、版本判断”四大块组织

根目录文档将优先回答维护者最常见的问题：
- 新建节点时面板要准备什么参数；
- 不同协议的提交体长什么样；
- 修改或迁移节点时复用了哪些字段；
- 为什么 x-ui 的 vless 要看版本号。

原因：
- 用户点名要求“新建节点、修改节点、面板参数、版本号判断”作为重点。
- 按代码顺序书写会被重复流程淹没，不利于检索。

备选方案：
- 按函数逐段说明。
- 放弃原因：重复度高，难以形成统一结论。

### 决策 3：将重复流程合并为“主路径 + 复用点”说明

文档不会机械罗列每个重复代码块，而是抽象为以下主路径：
- 新建节点主路径
- 续费/更新时间主路径
- 单节点改面板主路径
- 整单改面板主路径

并附上对应代码位置，说明哪些流程共享同一组参数转换逻辑。

原因：
- `users/views.py` 中有多处几乎相同的代码，如果逐块复制会导致文档冗长且难维护。

备选方案：
- 为每个代码块单独建章节。
- 放弃原因：无法突出真正的行为差异。

### 决策 4：对字段解释明确标记“代码确认”和“推断”

像 `panel_info`、`host_config`、`config_text`、`form_data`、`settings.clients[0].flow` 这类字段的含义会优先按代码读取得出；只有当字段命名可读但没有直接注释时，才以“推断”口径说明。

原因：
- 避免把静态分析结论包装成确定事实。
- 与此前中转接口文档的表达方式保持一致。

## Risks / Trade-offs

- [风险] `users/views.py` 存在多处重复实现，文档抽象后可能遗漏某个特殊分支。 → 缓解：每个结论都附主要代码位置，且优先归纳多处重复出现的共同逻辑。
- [风险] 某些字段意义只能从命名猜测，例如 3x-ui 路由规则中的 `tag`。 → 缓解：在文档中明确区分“代码确认”和“基于调用方式推断”。
- [风险] 版本判断只看到 `25.3.6` 这一特殊分支，未来版本可能继续扩展。 → 缓解：把当前实现如实记录为“硬编码版本分支”，不做额外泛化。
- [风险] OpenSpec 的 schema 偏向行为变更，而本次主要产出文档。 → 缓解：将 capability 定义为“项目内部参考文档能力”，把可交付物和验收点写清楚。

## Migration Plan

1. 创建 OpenSpec 变更工件，固化本次文档能力的范围。
2. 从现有代码提取 x-ui/3x-ui 的创建、更新、迁移和版本判断逻辑。
3. 在仓库根目录生成 Markdown 文档。
4. 用 `git status` 验证本次仅产生文档与 OpenSpec 变更文件。

本次变更不涉及部署、数据迁移和回滚；如需回退，只需删除新增文档和对应 OpenSpec change。
